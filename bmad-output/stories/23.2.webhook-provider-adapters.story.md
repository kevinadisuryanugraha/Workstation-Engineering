# 23.2: Webhook Adapter Multi-Provider (GitLab & Bitbucket) — Verifikasi & Normalisasi

**Story ID:** 23.2
**Epic:** 23 — Multi-Provider Git (Course Correction 8, Master PRD §30 Fase V2)
**Slug:** webhook-provider-adapters
status: done

## Story

As a **Platform Admin**,
I want **webhook dari GitLab dan Bitbucket diterima, diverifikasi, dan dinormalisasi ke satu model kanonik internal yang sama dengan GitHub**,
so that **seluruh pipeline evidence WORKSTATION tidak perlu tahu perbedaan format payload antar provider**.

## Acceptance Criteria

<!-- LOCKED -->

1. Route BARU `POST /api/v1/webhooks/gitlab` dan `POST /api/v1/webhooks/bitbucket` di `git.routes.ts`. Route lama `POST /api/v1/webhooks/github` TIDAK diubah perilakunya (regression wajib).
2. **Verifikasi per provider** (`webhook.crypto.ts` diperluas, API lama `verifyGitHubSignature` tetap utuh):
   - GitLab: header `X-Gitlab-Token` dibandingkan secret repo (konstanta-time, `crypto.timingSafeEqual`) — GitLab tidak memakai HMAC.
   - Bitbucket: header `X-Hub-Signature` (format `sha256=<hmac>`) diverifikasi HMAC-SHA256 terhadap raw body.
   - Lookup secret: by `(provider, repoFullName)` dari tabel `repositories` via repository registry (23.1); fallback env `GITLAB_WEBHOOK_SECRET` / `BITBUCKET_WEBHOOK_SECRET` bila repo belum teregistrasi (pola fallback global secret GitHub eksisting). Tidak cocok → 401 `INVALID_SIGNATURE`.
3. **Header identifikasi per provider:** GitLab memakai `X-Gitlab-Event` (nilai `Push Hook`, `Merge Request Hook`, `Tag Push Hook`) + `X-Gitlab-Event-UUID` sebagai delivery ID (bila absen: delivery ID deterministik = SHA-256 dari raw body + header event, dicatat jujur di delivery `error`/metadata bahwa ID ini sintetis). Bitbucket memakai `X-Event-Key` (`repo:push`, `pullrequest:created|updated|fulfilled|rejected`) + `X-Request-UUID`.
4. **Normalizer `webhook.providers.ts` (BARU):** memetakan payload mentah tiap provider → model kanonik tunggal `{ provider, repoFullName, event: 'push' | 'merge_request', ref?, commits: [{ sha, message, author, url? }], mergeRequest?: { number, title, sourceBranch, state?, url? } }`:
   - GitLab push: `project.path_with_namespace`, `ref`, `commits[]`; MR: `object_attributes.{iid,title,source_branch,state,url}`.
   - Bitbucket push: `repository.full_name`, `push.changes[].commits[]` (nested — wajib di-flatten), branch dari `changes[].new.name`; PR: `pullrequest.{id,title,source.branch.name,state,links.html.href}`.
   - Event di luar yang didukung → diterima 202 + delivery berstatus `IGNORED` (jujur, bukan gagal).
5. **Ingest idempoten:** delivery disimpan ke `webhook_deliveries` dengan kolom `provider` (23.1) terisi; dedup via `deliveryId` unik (idempotent bypass 200 untuk duplikat — perilaku ADR-005 sama). Respons cepat 202 (<50ms) sesuai kontrak ADR-005.
6. `npm run lint` + seluruh test hijau; test baru di `tests/webhook-providers.test.ts`: fixture payload GitLab push/MR & Bitbucket push/PR (salin struktur resmi), verifikasi token/HMAC benar+salah (401), idempotensi delivery, normalisasi kanonik (nested commits Bitbucket ter-flatten), event tak dikenal → IGNORED, regression `/webhooks/github`.

## Dev Notes

- **ADR-005 tetap menjadi konteks arsitektur:** dua tahap (verifikasi cepat <50ms → proses asinkron), idempoten via delivery ID. Story ini HANYA tahap 1 (ingest+normalisasi); pemrosesan kanonik ke tabel commits/pull_requests adalah 23.3.
- JANGAN memecah handler GitHub eksisting — buat handler generik yang dipakai 3 route; jika refactor berisiko, biarkan handler GitHub apa adanya dan buat handler generik baru untuk GitLab/Bitbucket (minimum blast radius menang).
- Timing-safe compare wajib untuk token GitLab (jangan `===` pada secret).
- Payload mentah tetap disimpan penuh di `webhook_deliveries.payload` (forensik), bentuk kanonik disimpan di properti `canonical` di dalam payload JSON yang sama.
- `X-Gitlab-Token` versi GitLab lama tidak selalu mengirim `X-Gitlab-Event-UUID` — fallback ID sintetis WAJIB deterministik agar retry GitLab tetap ter-dedup.
- Pola raw body lihat handler GitHub eksisting (`req.rawBody`).

## Testing

- Unit: verifikasi HMAC Bitbucket & token GitLab (benar/salah/secret Salah-repo), normalizer (flattening nested Bitbucket, MR GitLab), delivery ID fallback deterministik.
- Integration (DB tersedia): POST kedua route → 202 + baris delivery dengan provider benar; kirim ulang → 200 duplicate; event tak dikenal → IGNORED.
- Permission: route webhook publik (dilindungi signature) — sama seperti GitHub.
- Regression: `/webhooks/github` seluruh test lama hijau; full suite hijau; lint bersih.
