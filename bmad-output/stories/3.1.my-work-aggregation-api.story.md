# 3.1: Developer "My Work" Aggregation Endpoint & Workspace Data Feed

**Story ID:** 3.1  
**Epic:** 3 — Developer Experience & "My Work" Workspace  
**Slug:** my-work-aggregation-api  
status: ready-for-dev  

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Developer**,  
I want **a single aggregated API endpoint (`GET /api/v1/my-work`) that fetches all my assigned work items, assigned tickets, pending PR reviews, and recent activity**,  
so that **my workspace loads in one fast round-trip without opening multiple dashboard tabs**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Endpoint `GET /api/v1/my-work` (dilindungi `PERM_VIEW_ENGINEERING`) mengidentifikasi user aktif dari Bearer JWT token.
2. Respons endpoint mengembalikan struktur gabungan dalam standard envelope ADR-004:
   - `workItems`: Daftar work item aktif yang di-assign ke user (status bukan `DONE` dan bukan `CANCELLED`), diurutkan berdasarkan priority (P0 → P3).
   - `tickets`: Daftar tiket yang di-assign ke user (status bukan `RESOLVED` dan bukan `CLOSED`), diurutkan berdasarkan severity/priority.
   - `pendingReviews`: Daftar Pull Request di mana user terdaftar sebagai reviewer yang belum memberikan approval.
   - `recentActivity`: 10 aktivitas/event terakhir yang melibatkan user.
3. Waktu respons query agregasi < 150 ms (p95) berkat penggunaan index pada kolom `assignee_id` dan `status`.
4. Mendukung filter opsional `?projectId=...` untuk menyaring beban kerja per proyek spesifik.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. -->

- **Approach:** Integration testing dengan user sesi aktif dan data terhubung.
- **Key scenarios:**
  1. User A login → memanggil GET `/api/v1/my-work` → hanya melihat work item & tiket miliknya, bukan milik User B.
  2. Item dengan status `DONE` tidak muncul di daftar tugas aktif.
  3. Query merespons dalam < 150ms pada dataset tes.
