# 7.1: Append-Only Audit Logging Middleware with Correlation IDs

**Story ID:** 7.1  
**Epic:** 7 — Audit Trail & System Governance  
**Slug:** append-only-audit-middleware  
status: done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->  

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Platform Admin / Security Officer**,  
I want **every incoming request assigned a unique correlation ID and every sensitive mutation logged to an append-only audit table in PostgreSQL**,  
so that **there is an immutable forensic history of who did what, when, and from where**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Middleware `requestCorrelationId` menyematkan `X-Correlation-Id` (UUIDv7 atau UUIDv4) pada setiap incoming request dan header response.
2. Skema Drizzle `audit_logs` didefinisikan dengan kolom: `id`, `actor_id`, `actor_name`, `action`, `target_entity`, `target_id`, `details` (JSONB diff), `ip_address`, `correlation_id`, dan `created_at` (default now).
3. Modul `auditService.logEvent(entry)` menyimpan record audit secara persisten ke database tanpa menyediakan fungsi update atau delete (*append-only*).
4. Event sistem kritis berikut wajib memicu pemanggilan `auditService.logEvent`:
   - `AUTH_LOGIN_SUCCESS` & `AUTH_LOGIN_FAILED`
   - `PROJECT_CREATED` & `PROJECT_STATUS_CHANGED`
   - `WORK_ITEM_DELETED`
   - `DEPLOYMENT_ROLLBACK_EXECUTED`
5. Jika pencatatan audit log gagal saat transaksi sensitif, operasi mutasi tidak boleh diam-diam mengabaikannya tanpa catatan error di logger server.

  2. Pemanggilan `auditService.logEvent` menghasilkan baris baru di tabel `audit_logs`.
  3. Attempting to update or delete rows in `audit_logs` is not supported by the service API.
