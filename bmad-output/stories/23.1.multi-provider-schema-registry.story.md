# 23.1: Multi-Provider Git — Skema Provider & Repository Registry API

**Story ID:** 23.1
**Epic:** 23 — Multi-Provider Git (Course Correction 8, Master PRD §30 Fase V2 "multi-provider Git")
**Slug:** multi-provider-schema-registry
status: done

## Story

As a **Tech Lead**,
I want **mendaftarkan repositori GitLab dan Bitbucket ke project, selain GitHub, melalui satu API registry yang sama**,
so that **evidence commit/MR dari semua provider Git tim dapat terkumpul di WORKSTATION tanpa duplikasi sistem ingest**.

## Acceptance Criteria

<!-- LOCKED -->

1. Migration `0017_add_provider_fields.sql` (BARU): tabel `repositories` ditambah kolom `provider` varchar(20) NOT NULL DEFAULT 'GITHUB'; tabel `webhook_deliveries` ditambah kolom `provider` varchar(20) NOT NULL DEFAULT 'GITHUB'. Tanpa breaking change ke tabel/payload eksisting — data lama otomatis GITHUB.
2. Drizzle schema `repositories.ts` & `webhook_deliveries.ts` diperbarui dengan kolom `provider` + tipe union `GitProvider = 'GITHUB' | 'GITLAB' | 'BITBUCKET'` diekspor dari `repositories.ts`.
3. Endpoint BARU `GET /api/v1/git/repositories` (auth-only `authenticateToken`, pola 18.1): daftar repositori terdaftar dengan `{ id, projectId, fullName, provider, defaultBranch, createdAt }` — **webhookSecret TIDAK pernah dikirim ke client** (hanya indikator boolean `hasSecret`). Filter `?projectId` didukung. Envelope standar `{ success, data, error, meta }`.
4. Endpoint BARU `POST /api/v1/git/repositories` (requirePermission `PERM_EVIDENCE_ATTACH` — registrasi repo = provisioning sumber evidence): body `{ projectId, fullName, provider, defaultBranch? }` divalidasi zod ketat — `provider` harus salah satu dari enum (di luar enum → 400), `fullName` pola `owner/repo` (maks 255), `projectId` harus ada di DB (tidak ada → 404). `webhookSecret` digenerate server (`crypto.randomBytes` hex) bila tidak dikirim. Respons 201 berisi repo TANPA secret mentah (secret tidak dikirim ulang; cukup `hasSecret: true`).
5. Idempoten: registrasi `projectId + provider + fullName` yang sudah ada TIDAK membuat duplikat — mengembalikan 200 dengan repo eksisting (polanya sama seperti idempotensi konversi 16.3). `fullName` yang sama dengan provider BERBEDA boleh co-eksis (repo mirror lintas provider).
6. Audit trail: POST registrasi tercatat via audit middleware append-only eksisting (correlation ID UUIDv7) — tanpa mekanisme audit baru.
7. `npm run lint` + seluruh test hijau; test baru di `tests/repository-registry.test.ts`: migrasi kolom (up, default GITHUB untuk baris lama), validasi enum provider tolak 400, project tak dikenal 404, idempotensi 200-vs-201, secret tidak pernah muncul di respons, 403 tanpa permission write (pola skip-guard CI tanpa DATABASE_URL).

## Dev Notes

- **Sumber requirement:** Master PRD §30 — Fase V2 mencantumkan "multi-provider Git" sebagai scope V2; sebelumnya ditunda eksplisit di epics Epic-5 ("Multi-provider Git selain GitHub ditunda ke V2"). CC-8 membukanya kini.
- **Permission:** matriks RBAC 9 role × 20 permission TIDAK diubah (mengikuti keputusan 22.1). `PERM_EVIDENCE_ATTACH` dipakai karena repo = sumber evidence (dimiliki Super Admin, Org Admin, Tech Lead, Project Manager). Jika saat implementasi fit ini keliru, catat penyimpangan di Dev Agent Record mengikuti pola 22.1 — JANGAN menambah permission baru.
- kolom `provider` default 'GITHUB' menjamin baris lama dan seluruh alur Epic-5/18.1 tidak berubah perilaku (backward compatible).
- Secret webhook: server-side generate + lookup by (provider, fullName) saat verifikasi di 23.2. Jangan pernah mengirim secret ke client, jangan log secret.
- Ikuti pola envelope + `safeAsync` + zod dari `work-item.routes.ts` / `git-entity.routes.ts`.
- Drizzle: salin konvensi migrasi manual dari `0016_add_debt_fields.sql` + update `server/db/migrations/meta` (pola 22.1).
