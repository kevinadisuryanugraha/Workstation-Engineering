# 4.1: Ticketing / ITSM Lifecycle & Triage API

**Story ID:** 4.1  
**Epic:** 4 — Ticketing & ITSM Issue Resolution  
**Slug:** ticket-lifecycle-api  
status: ready-for-dev  

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Tech Lead / Support Specialist / QA**,  
I want **a dedicated Ticketing API supporting issue intake, distinct Severity and Priority fields, and a formalized status lifecycle**,  
so that **user bugs, infrastructure issues, and technical requests are triaged and tracked formally without getting lost in chat groups**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Skema Drizzle `tickets` dibuat di PostgreSQL dengan field: `id`, `key` (unik, misal `TCK-101`), `project_id`, `requester_id`, `assignee_id`, `type` (BUG, FEATURE_REQUEST, TECHNICAL_ISSUE, MAINTENANCE, SECURITY, PERFORMANCE, INCIDENT), `severity` (Critical, High, Medium, Low), `priority` (P0, P1, P2, P3), `status` (NEW, TRIAGED, ASSIGNED, IN_PROGRESS, IN_REVIEW, READY_FOR_TEST, TESTING, RESOLVED, CLOSED, CANCELLED), `title`, `description`, `created_at`, `updated_at`.
2. Endpoint `POST /api/v1/tickets` (dilindungi `PERM_TICKET_CREATE`) membuat tiket baru dengan status default `NEW` dan severity wajib terisi.
3. Endpoint `PATCH /api/v1/tickets/:id/triage` (dilindungi `PERM_TICKET_UPDATE`) mengizinkan Tech Lead / PM menetapkan `assigneeId`, `priority`, dan mengubah status ke `ASSIGNED` atau `IN_PROGRESS`.
4. Endpoint `GET /api/v1/tickets` mendukung filter berdasarkan `projectId`, `severity`, `status`, dan pagination.
5. Transisi status tiket ke `RESOLVED` (dilindungi `PERM_TICKET_RESOLVE`) wajib menyertakan resolusi atau penjelasan penanganan masalah.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from planning docs with citations. -->

- **Requirements Citation:** FR-007 Tiket Masuk, Workflow, dan Triage. [Source: prd.md#FR-007]
- **Severity vs Priority:** Severity menggambarkan dampak teknis/bisnis masalah; Priority menggambarkan urutan antrian pengerjaan oleh tim dev. Keduanya disimpan di kolom terpisah. [Source: prd.md#FR-007]
- **Key Generation:** Format key adalah `TCK-{SEQUENCE}` atau `{PROJECT_KEY}-T{SEQUENCE}`. [Source: architecture.md#5.1]
- **Permission Matrix:**
  - Create: `PERM_TICKET_CREATE` (Support, QA, Dev, PM, Admin)
  - Update/Triage: `PERM_TICKET_UPDATE` (Tech Lead, PM, Admin)
  - Resolve: `PERM_TICKET_RESOLVE` (Tech Lead, QA, PM, Admin). [Source: architecture.md#ADR-003]

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. -->

- **Approach:** Integration test lifecycle status tiket.
- **Key scenarios:**
  1. Tiket baru tercipta dengan status `NEW`.
  2. Triage berhasil menetapkan assignee dan priority, mengubah status ke `ASSIGNED`.
  3. Role `Viewer` ditolak saat mencoba membuat atau mengupdate tiket.
  4. Penyelesaian tiket tanpa keterangan resolusi ditolak dengan pesan validasi yang jelas.
