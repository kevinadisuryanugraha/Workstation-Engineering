# 10.1: Operational Report Aggregation API

**Story ID:** 10.1
**Epic:** 10 — Dual-Language Reporting Engine
**Slug:** report-aggregation-api
status: ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Manager / PM**,
I want **an API that aggregates operational KPIs (tickets, work items, deployments, audit activity) for an arbitrary period**,
so that **management reports are generated from real platform data instead of manual bookkeeping**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Endpoint `GET /api/v1/reports/summary?from=<ISO>&to=<ISO>` (RBAC: Tech Lead, PM, Manager, Admin — Developer & Viewer ditolak 403) mengembalikan satu objek agregat periode.
2. Agregasi mencakup minimal:
   - **Tickets:** total per status, per severity, jumlah triase (ASSIGNED), jumlah resolved/closed.
   - **Work items:** total per status dan per type (epic/feature/task/bug/tech-debt).
   - **Deployments:** jumlah deployment per environment, jumlah rollback.
   - **Audit:** jumlah event per action type (top 5).
3. Parameter `from`/`to` wajib valid ISO 8601 dengan `from < to`; invalid → `HTTP 400`. Default periode = 7 hari terakhir bila kosong.
4. Semua angka dihitung dari PostgreSQL (query Drizzle dengan filter rentang pada kolom timestamp masing-masing tabel) — tanpa data mock.
5. Response memuat metadata: `from`, `to`, `generatedAt`, dan `correlationId` request.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. -->

- **Approach:** Integration test dengan seed data periodik; verifikasi angka pasti (bukan "ada datanya").
- **Key scenarios:**
  1. Seed 3 tiket (2 open, 1 resolved) + 4 work item + 2 deployment (1 rollback) dalam periode → angka agregat persis.
  2. Data di luar rentang `from`/`to` tidak terhitung.
  3. Role Developer → HTTP 403; periode invalid → HTTP 400.
