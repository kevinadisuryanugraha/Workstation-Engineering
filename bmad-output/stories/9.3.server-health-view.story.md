# 9.3: Server Health Dashboard View

**Story ID:** 9.3
**Epic:** 9 — Workstation Linux Server Agent
**Slug:** server-health-view
status: ready-for-dev   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Tech Lead**,
I want **a dashboard view showing live health cards and metric history for every monitored server**,
so that **I can spot resource pressure on office servers and the Kontabo VPS at a glance**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Endpoint `GET /api/v1/server-metrics` (RBAC: persetujuan minimal sama seperti audit viewer — Developer boleh lihat, Viewer ditolak 403) mengembalikan daftar server unik + metrik terakhir masing-masing + flag stale (`recordedAt` > 2× interval → `stale: true`).
2. Endpoint `GET /api/v1/server-metrics/:serverName/history?hours=24` mengembalikan deret metrik untuk grafik/riwayat (default 24 jam, maks 168).
3. Komponen UI baru `src/components/ServerHealthView.tsx` menampilkan kartu per server: nama, CPU %, RAM %, disk paling penuh %, badge status (OK / WARNING ≥ 80% / STALE), dan daftar riwayat ringkas 24 jam terakhir.
4. View terintegrasi ke navigasi dashboard existing (mengikuti pola view AuditLogView) dan mengambil data via React Query hook baru.
5. Kondisi kosong (belum ada agen yang melapor) menampilkan empty state yang jelas, bukan error.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from planning docs with citations. -->

- **Permissions:** ikuti matriks ADR-003; lihat metrik server adalah operasi read-only operasional — gunakan permission read yang sudah ada bila cocok, atau daftarkan `PERM_SERVER_METRICS_VIEW` di `server/constants/permissions.ts` mengikuti pola `PERM_AUDIT_LOGS_VIEW`. [Source: architecture.md#ADR-003, stories/7.2.audit-log-viewer-api.story.md]
- **UI pattern:** salin struktur data-fetch + empty state dari `src/components/AuditLogView.tsx` agar konsisten. [Source: stories/7.2.audit-log-viewer-api.story.md]
- **Threshold:** WARN ≥ 80% dan STALE > 2× `AGENT_INTERVAL_SECONDS` (default > 120s) — sederhana dan deterministik. [Source: stories/9.1.agent-metrics-daemon.story.md]
- **Skala data:** riwayat 24 jam @60s ≈ 1.440 titik; kembalikan apa adanya (JSON ringan), agregasi di klien.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. -->

- **Approach:** Integration test API (RBAC + bentuk data) dan uji render komponen bila setup sudah tersedia; fokus kontrak data.
- **Key scenarios:**
  1. Developer → HTTP 200 daftar server; Viewer → HTTP 403.
  2. Server tanpa data > 2× interval → `stale: true`.
  3. `history?hours=24` default; `hours=999` dibatasi/ditolak 400.
  4. Database kosong → response sukses dengan array kosong (UI empty state).
