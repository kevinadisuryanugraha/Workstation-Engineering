# 8.2: Instant Token Revocation via `token_version` (SEC-01)

**Story ID:** 8.2
**Epic:** 8 — Security Hardening & Token Governance
**Slug:** token-revocation-token-version
status: done   <!-- lifecycle: backlog -> ready-for-dev -> in-progress -> review -> done -->

> Owned by planning until `ready-for-dev`. Sized to one dev-day (~2-8h). No story points.

## Story

As a **Security Admin**,
I want **issued JWT tokens to become instantly invalid when the user logs out or their role/permissions change**,
so that **a revoked or demoted employee can never reuse an old token for up to 24 hours**.

## Acceptance Criteria

<!-- LOCKED. Numbered, testable. External dev tools must not edit. -->

1. Tabel `users` memiliki kolom integer `token_version` (default `1`, not null) via migrasi Drizzle.
2. JWT yang diterbitkan saat login menyertakan claim `tokenVersion` dari DB.
3. Middleware `authenticate` **menolak** token yang klaim `tokenVersion`-nya tidak sama dengan nilai terkini di DB (`HTTP 401`), meskipun signature valid dan belum kedaluwarsa.
4. Proses **logout** menaikkan `token_version` user di DB (`+1`) sehingga semua token lama mati seketika.
5. Perubahan **role/permissions** pada user juga menaikkan `token_version` sehingga token lama dengan hak lama tidak berlaku.
6. Login kembali setelah logout berhasil menghasilkan token baru yang valid.

## Dev Notes

<!-- LOCKED. Concrete guidance compiled from planning docs with citations. -->

- **Requirements Citation:** SEC-01 — token stateless murni 24 jam tidak dapat dicabut. [Source: docs/DEEP-SCAN-REPORT-2026-09-18.md#SEC-01]
- **Pola yang dipilih:** kolom `token_version` di PostgreSQL (bukan Redis) — konsisten ADR-002 & out-of-scope Epic 8. [Source: bmad-output/epics.md#Epic-8, architecture.md#ADR-002]
- **Kinerja:** verifikasi versi menambah 1 query `SELECT token_version` per request ter-autentikasi; pastikan lookup by primary key (murah). ADR-003 tetap berlaku — token tetap stateless-signature, versi bersifat pengecekan otoritas. [Source: architecture.md#ADR-003]
- **Kompatibilitas:** token lama tanpa claim `tokenVersion` harus ditolak (anggap versi 0 ≠ versi DB ≥ 1) agar tidak ada celah masa transisi.

## Testing

<!-- LOCKED. STRATEGY ONLY — what to verify and how. -->

- **Approach:** Integration testing siklus penuh: login → pakai token → logout → pakai token lama (401) → login lagi → token baru valid.
- **Key scenarios:**
  1. Setelah logout, request dengan token lama → HTTP 401.
  2. Setelah role user diubah oleh admin, token lama user → HTTP 401.
  3. Token lama tanpa claim `tokenVersion` (simulasi token pra-migrasi) → HTTP 401.
  4. Token aktif yang valid tetap lulus (tidak ada regresi pada suite auth existing).
