# 23.3: Pemrosesan Kanonik Multi-Provider — Commits, MR/PR & Evidence Links

**Story ID:** 23.3
**Epic:** 23 — Multi-Provider Git (Course Correction 8, Master PRD §30 Fase V2)
**Slug:** git-linker-canonical-processing
status: done

## Story

As a **Developer**,
I want **commit dan merge request dari GitLab/Bitbucket otomatis tersimpan dan terhubung ke tiket/work item lewat kode item di pesan commit atau judul MR — persis seperti yang sudah terjadi untuk GitHub**,
so that **traceability Tiket → Work Item → Commit → MR berlaku setara di semua provider yang dipakai tim**.

## Acceptance Criteria

<!-- LOCKED -->

1. `webhook.service.ts` (tahap 2 pemrosesan) mengonsumsi payload kanonik 23.2 dan mengisi tabel `commits` dan `pull_requests` untuk SEMUA provider (GitHub kini juga lewat jalur kanonik ATAU tetap lewat jalur lamanya — dev memilih yang meminimalkan risiko regression; yang penting: hasil akhir tabel identik dan test lama hijau).
2. Lookup repo: by `(provider, fullName)` di tabel `repositories`. Repo belum teregistrasi → delivery berstatus `FAILED` dengan pesan error jujur `REPO_NOT_REGISTERED` (bukan crash, bukan data yatim tanpa repo).
3. `pull_requests` menerima MR GitLab (`object_attributes.iid` → nomor PR) dan PR Bitbucket (`pullrequest.id` → nomor PR); kolom URL/state/branch terisi dari model kanonik. Commit: `sha`, `message`, `author`, `repoId` terisi untuk semua provider.
4. **Git entity auto-linker (`git-linker.service.ts` + `entity-parser.ts`) bekerja pada model kanonik** — regex kode item (`\b[A-Z]{2,10}-\d{1,6}\b`) dijalankan terhadap message commit & judul MR/PR semua provider; `evidence_links` terisi dua arah persis perilaku GitHub eksisting (5.2). Regex TIDAK berubah.
5. Delivery status lifecycle: `PENDING → PROCESSED` bila entity + evidence tersimpan; `FAILED` + pesan error terstruktur bila lookup/linking gagal (pola ADR-005 tahap 2). Push branch tak berkode item → PROCESSED tanpa evidence (bukan gagal).
6. Read API 18.1 (`GET /api/v1/git/commits` & `/pull-requests`) kini menyertakan `provider` (join `repositories`) pada tiap item — additive, kontrak field lama tidak berubah.
7. `npm run lint` + seluruh test hijau; test baru di `tests/git-linker-providers.test.ts`: fixture kanonik GitLab & Bitbucket → baris commits/pull_requests benar, evidence link via kode item di message MR Bitbucket & commit GitLab, REPO_NOT_REGISTERED → FAILED jujur, read API mengembalikan `provider`, regression evidence GitHub.

## Dev Notes

- **Prinsip Master PRD (traceability):** evidence harus dapat ditelusuri — data tanpa repo terdaftar TIDAK boleh ditulis diam-diam; FAILED jujur lebih baik daripada commit yatim.
- Skema `commits` & `pull_requests` TIDAK ditambah kolom di story ini (cukup untuk model kanonik; jika terbukti butuh, catat di Dev Agent Record dan stop — jangan improvisasi migrasi baru tanpa persetujuan).
- Jalur GitHub: memilih "GitHub juga lewat jalur kanonik" dianjurkan (satu jalur pemrosesan, pemeliharaan lebih murah) — TAPI hanya jika regression 5.x/5.2 tetap hijau penuh; kalau tidak, jalankan dual-path dan catat keputusan.
- Idempotensi persist: commit SHA unik per repo — `onConflictDoNothing` / cek-then-insert agar retry delivery tidak menduplikasi baris (pola 5.1).
- Jangan sentuh `webhook.crypto.ts` / `webhook.providers.ts` (milik 23.2) kecuali membaca.
