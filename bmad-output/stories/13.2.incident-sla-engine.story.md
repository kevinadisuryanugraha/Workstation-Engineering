# 13.2: Incident SLA Engine — Response/Resolution Targets & Breach Detection

**Story ID:** 13.2
**Epic:** 13 — Incident Room & SLA Management
**Slug:** incident-sla-engine
status: done

## Story

As a **Manager**,
I want **every incident measured against severity-based response and resolution time targets with automatic breach detection**,
so that **incident handling accountability is objective and visible**.

## Acceptance Criteria

<!-- LOCKED -->

1. Target SLA per severity terpusat di `server/modules/incidents/incident.sla.ts`: CRITICAL (tanggap 15 menit, selesai 4 jam), MAJOR (30 menit, 8 jam), MINOR (2 jam, 24 jam) — single source of truth, dapat diimpor test.
2. Response time = `acknowledgedAt - detectedAt`; resolution time = `resolvedAt - detectedAt`. Status per dimensi: `PENDING` (belum ada timestamp), `MET`, atau `BREACHED` (melebihi target).
3. `GET /api/v1/incidents` dan `/:id` menyertakan objek `sla: { response: { targetMinutes, status, actualMinutes|null }, resolution: { targetMinutes, status, actualMinutes|null } }`.
4. Insiden CRITICAL yang sudah lewat target response tanpa acknowledgedAt tetap `PENDING` namun menyertakan `overdueMinutes` (sudah lewat berapa menit dari target) agar UI bisa menandai merah.
5. SLA murni dihitung on-read dari timestamp yang sudah ada — tidak ada job background pada fase ini.

## Tasks / Subtasks

- [ ] Modul SLA murni (AC: #1, #2, #4) — `computeIncidentSla(severity, detectedAt, acknowledgedAt, resolvedAt, now?)` pure function + target matrix
- [ ] Integrasi service (AC: #3) — sertakan sla pada list & detail
- [ ] Tests — `tests/incident-sla.test.ts` (matriks lengkap per severity, PENDING/MET/BREACHED, overdueMinutes, deterministik via injected now)

## Testing

- **Key scenarios:**
  1. CRITICAL acknowledged 10 menit → response MET; 20 menit → BREACHED.
  2. MAJOR resolved 7 jam → resolution MET; 9 jam → BREACHED.
  3. Tanpa acknowledgedAt → PENDING + overdueMinutes dihitung.
  4. ActualMinutes dibulatkan ke bawah (menit utuh).
